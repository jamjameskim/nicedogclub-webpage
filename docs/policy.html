#1. 이 문서의 성격

이 문서는 서비스 상세 기획안의 §28("출시 전 반드시 확정할 정책")을 구체화한 것이다. 두 종류의 내용이 섞여 있다 — 이미 코드로 구현되어 실제로 작동 중인 정책(예: 차단 시 양방향 비노출)과, 사용자 규모가 커지기 전에 반드시 사업·법무 확정이 필요한 항목(예: 데이터 보존 기간)이다. 후자는 확정 필요로 명확히 표시했고, 이 문서 자체가 그 확정을 대신하지 않는다 — 확정되면 이 문서와 실제 코드를 함께 갱신해야 한다.

#2. 개인정보·위치데이터 처리 구현됨

2.1 수집하는 위치 데이터의 종류

종류정확도공개 범위
산책 경로(walks.path)GPS 원본(약 2m 간격)본인만 조회(RLS). 타인에게는 절대 원본 행이 안 나가고, 집계값(총 거리·자주 다니던 곳 격자)만 관계 있는 상대에게 노출
프로필 위치(profiles.neighborhood/home_lat/lng)약 1km 격자로 뭉갬동 이름은 같은 동 분실 알림 대상 판정에, 좌표는 표시하지 않음
분실 신고 마지막 목격 위치정확 좌표신고를 본 사람 전원에게 지도+주소 텍스트로 공개(찾기라는 목적상 불가피)
목격 제보 위치제보자가 입력한 좌표 또는 텍스트보호자에게만 전달, 공개 지도(주변 탭)에는 안 뿌림
게스트 웹 제보 위치텍스트만(자유 입력)브라우저 GPS 자동입력은 의도적으로 뺐음 — 폼 작성 위치와 목격 위치가 다를 수 있어, 틀릴 수 있는 좌표보다 정직한 텍스트가 안전하다는 판단

2.2 최소 공개 원칙의 실제 적용

  • 산책 경로 원본 위경도 배열은 절대 타인에게 API로 반환하지 않는다 — 모든 교차 사용자 조회는 SECURITY DEFINER 함수를 통해 집계된 숫자(총 거리, 격자 카운트)만 반환한다.
  • 동네친구·모임 매칭도 정확한 실시간 위치가 아니라, 지나간 산책 경로가 40m·±20분 이내로 겹쳤는지만 서버 함수 내부에서 판정하고 그 판정 결과(매칭 여부)만 클라이언트에 돌려준다.
  • 사용자 홈 위치는 정확 좌표가 아니라 약 1km 격자로 뭉개서 저장한다 — 집 주소를 역으로 특정하기 어렵게 하기 위함.

2.3 제3자 제공 확정 필요

현재 위치 데이터를 외부 광고·분석 업체에 제공하지 않는다(애초에 분석 SDK 자체가 미도입, §24 참고). 다만 개인정보처리방침에 "제3자 제공 없음"을 명문화할지, 향후 분석 도구 도입 시 어떤 고지를 할지는 확정이 필요하다.

#3. 데이터 보존·삭제 정책 확정 필요

현재 코드에는 명시적인 TTL(자동 삭제 주기)이 없다 — 계정을 탈퇴하지 않는 한 대부분의 데이터가 무기한 보관된다. 아래는 확정이 필요한 제안 초안이다.

데이터현재 상태제안 보존 기간
산책 경로(GPS)무기한(로컬+서버)제안: 계정 존속 기간 내 무기한 유지(사용자 본인 자산으로 취급), 탈퇴 시 즉시 삭제
분실 신고(해결됨)무기한, route_distribution은 종료 시 삭제됨(구현됨)제안: 신고 자체는 통계 목적으로 익명화 후 보관, 개인 식별 정보는 1년 후 삭제
목격 제보(게스트 포함)무기한제안: 신고 해결 후 90일 뒤 위치 텍스트·사진 삭제, 통계만 유지
알림 발송 기록(notification_outbox)무기한제안: 90일 후 삭제(중복 방지 목적은 20시간 창이면 충분)
신고(reports) 내역무기한제안: 분쟁 대응 목적상 1~2년 보관 후 삭제
탈퇴 계정 데이터탈퇴 플로우는 있으나 완전 삭제 범위 미확정확정 필요: 즉시 하드 삭제 vs. 30일 유예 후 삭제

#4. 콘텐츠 신고·차단 운영 구현됨

4.1 신고(reports)

  • insert-only 테이블 — 신고자는 자신이 낸 신고를 조회·수정할 수 없다(재신고 압박 방지 목적이 아니라, 신고 내용이 신고 대상에게 새어나갈 경로를 원천 차단하기 위함).
  • 운영자는 Supabase Table Editor로만 확인한다(전용 웹 콘솔 없음, §25).
  • 신고 사유 카테고리, 처리 SLA(예: 24시간 내 1차 검토)는 확정 필요.

4.2 차단(blocked_users)

  • 차단은 RESTRICTIVE RLS 정책으로 구현 — 일반적인 PERMISSIVE 정책 위에 "차단 관계가 있으면 무조건 제외"를 추가로 겹쳐서, 어떤 조회 경로(동네친구 목록, 주변 지도, 분실 알림 대상)로도 서로 보이지 않는다.
  • 차단은 양방향이다 — A가 B를 차단하면 B도 A를 못 본다. "누가 나를 차단했는지"는 어느 쪽도 알 수 없다.
  • 차단 해제 시 기존 하트·매칭 기록이 복원되는지는 확정 필요(현재는 재매칭 로직을 다시 타야 함).

#5. 커뮤니티 가이드라인 확정 필요

현재 앱 내에 별도의 "커뮤니티 가이드라인" 화면은 없다. 동네친구·모임·하트라는 소셜 기능이 실제로 쓰이기 시작하면 아래 항목에 대한 명문화된 가이드라인과 앱 내 노출 지점(온보딩 또는 친구 탭 첫 진입)이 필요하다.

  • 사진에 사람 얼굴이 나오지 않게 안내(이미 "사람 프로필 사진 제거" 방향으로 정리된 선례 있음)
  • 타인의 반려견 사진을 무단으로 캡처·재배포하지 않기
  • 분실 신고·목격 제보에 허위 정보를 올리지 않기 — 이는 안전 기능이라 커뮤니티 가이드라인보다 강한 제재(§11) 대상
  • 하트·동네친구 매칭을 이용한 스토킹성 행동에 대한 명시적 금지 조항과 신고 경로 안내

#6. 하트·어뷰징 방지 구현됨 + 일부 확정 필요

6.1 구조적으로 막아둔 것

  • 관계 확인 없이는 하트를 줄 수 없다 — like_neighbor() 함수 내부에서 is_matched_with() 또는 shares_group_with()를 확인하고, 둘 다 아니면 예외를 던진다. 클라이언트에서 임의 target_id를 넣어도 서버가 거부한다.
  • 자기 자신에게 하트를 줄 수 없다 — 같은 함수 내부에서 명시적으로 막음.
  • 하루 1회 제한 — pet_likes 테이블의 unique(liker_id, target_id, liked_on) 제약으로 DB 레벨에서 강제(애플리케이션 로직 우회 불가).
  • 걸음 기반 하트는 위조 불가 — 클라이언트가 보내는 게 아니라, 서버에 저장된 walks.distance_m 합산값에서 매번 재계산한다(§9.3의 속도·정확도 필터를 이미 통과한 값).

6.2 아직 안 막은 것 확정 필요

  • 가짜 GPS(모의 위치)로 동네친구 매칭 자체를 조작해 하트를 우회 획득하는 경우 — 현재 별도 탐지 로직 없음. 규모가 작을 때는 리스크가 낮지만, 성장 시 모의위치 탐지(예: mock-location 플래그, 속도 이상치 패턴) 도입 필요.
  • 같은 사람이 여러 계정을 만들어 서로 하트를 주고받는 시나리오 — 계정당 반려견 1마리 전제와 결합하면 리스크는 제한적이나, 명시적 정책은 없음.

#7. 알림 정책 세부 구현됨

큰 구조는 기획안 §18 참고. 이 섹션은 사용자 동의·옵트아웃 관점만 다룬다.

카테고리옵트아웃 가능근거
safety(분실·목격·해결)불가생명·안전 관련 정보이므로 마케팅 동의와 분리해 항상 발송
social(하트·매칭·모임)가능(notify_marketing 토글)편의 기능이라 동의 기반
retention(다이제스트·산책 리마인더)가능(notify_marketing 토글)재방문 유도 목적이라 명확히 마케팅성으로 분류

social과 retention이 하나의 토글을 공유하는 것이 정보통신망법상 "광고성 정보"와 "서비스 이용에 필요한 정보"를 충분히 구분한 것인지는 확정 필요 — 필요 시 두 토글로 분리를 검토해야 한다.

#8. 미성년자·가입 자격 확정 필요

  • 온보딩에서 "만 14세 이상"에 체크하도록 되어 있으나(§6.2), 실제 연령 검증(예: 본인인증) 수단은 없다 — 자기 확인에 의존.
  • 법정대리인 동의가 필요한 연령대(만 14세 미만) 가입을 원천 차단할지, 혹은 별도 플로우를 둘지 확정 필요.
  • 목격 제보 게스트 웹페이지는 로그인 자체가 없어 연령 확인 장치가 전혀 없다 — 이 경로로 수집하는 정보를 "위치 텍스트, 시각, 사진, 메모"로 최소화한 현재 설계가 리스크 완화의 핵심이다.

#9. 사고 대응 절차 확정 필요

현재 전담 보안/개인정보 담당자가 지정되어 있지 않다(1인 운영). 아래는 최소 뼈대 제안이다.

  1. 탐지: Supabase 대시보드 알림, 사용자 신고, 또는 비정상 쿼리 패턴으로 인지
  2. 격리: 문제가 된 RLS 정책·RPC 함수는 revoke execute로 즉시 차단 가능(코드 배포 없이 SQL만으로)
  3. 영향 범위 확인: 어떤 테이블/사용자가 영향을 받았는지 SQL로 확인
  4. 통지: 개인정보 유출 시 개인정보보호법상 통지 의무 대상·기한 확인(72시간 기준 등) — 법무 확정 필요
  5. 재발 방지: docs/app-state.md에 원인과 조치를 기록(이미 코드베이스에 있는 습관을 사고 대응까지 확장)

#10. 제3자 데이터 이용 구현됨

  • 쓰레기통 위치: 공공데이터 포털 데이터 이용 — 출처·기준일을 상세 화면에 표시(§10.2). 이용 조건·갱신 주기 재확인은 확정 필요.
  • 지도 타일/역지오코딩: 카카오/구글 지도 SDK 이용 약관 범위 내에서만 사용.
  • 소셜 로그인: 카카오·구글 OAuth로 받는 정보는 이메일·닉네임 등 최소 범위만 요청.
