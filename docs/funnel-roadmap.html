#1. 왜 지금 이 문서인가

서비스 상세 기획안 §24는 분석 이벤트 트래킹이 "미구현"이라고 명시한다. 이벤트 SDK가 없다고 해서 측정이 불가능한 건 아니다 — 이미 Supabase에 쌓이고 있는 walks, lost_cases, sightings, pet_likes, notification_outbox 같은 원본 테이블만으로도 AARRR 퍼널의 상당 부분을 SQL로 바로 계측할 수 있다.

이 문서의 목표는 두 가지다. 첫째, 지금 당장 돈과 시간을 들이지 않고 SQL Editor에서 실행 가능한 임시 계측 쿼리를 제공한다. 둘째, 사용자가 늘면서 SQL만으로 부족해질 시점을 대비해 무료 티어부터 시작하는 단계적 도입 로드맵을 정의한다. 거의 풀타임으로 혼자 운영하고 마케팅 예산이 없다는, 앞서 논의된 "첫 결제 스프린트" 전제를 그대로 이어받는다.

#4. 계측 로드맵 3단계

Phase 1 — 무료, SQL 임시 계측 지금 바로

비용 0원. Supabase SQL Editor에서 §5의 쿼리를 주기적으로(주 1회 권장) 직접 실행해 숫자를 확인한다. 코드 변경 불필요 — 이미 쌓인 테이블만 조회한다. 단점: 실시간이 아니고, 클릭·화면조회 같은 "이벤트"는 애초에 안 남아서 볼 수 없다(예: 앱 오픈 수, 화면별 이탈률).

Phase 2 — 무료 티어 분석 SDK 도입 DAU 수백 단위부터 고려

PostHog(자체호스팅 또는 무료 클라우드 티어) 또는 Amplitude 무료 플랜 같은 이벤트 트래킹 SDK를 앱에 추가한다. §3의 "미계측" 표시된 이벤트(app_opened, 알림 탭, 링크 복사 등)를 실제로 클라이언트에서 track() 호출로 채운다. 이 시점부터 화면별 이탈, 세션 길이, 실시간 퍼널 시각화가 가능해진다. 비용: 무료 티어 이벤트 한도 내에서는 0원.

Phase 3 — 대시보드·코호트·A/B 테스트 유료 전환 검증 단계부터

"첫 결제 스프린트"에서 유료 기능이 실제로 붙는 시점과 맞물린다. 결제 전환 퍼널, 코호트별 리텐션 곡선, 기능 A/B 테스트가 필요해지면 유료 티어(PostHog/Amplitude 유료 플랜) 또는 자체 웨어하우스(Supabase → 간단한 BI 툴 연결)로 넘어간다. 이 단계는 실제 유료 사용자가 생긴 뒤에 투자를 정당화하는 것이 순서 — 미리 사지 않는다.

#5. Phase 1 — 지금 바로 실행 가능한 SQL 모음

모두 Supabase SQL Editor에 그대로 붙여넣어 실행 가능하다. 날짜 범위(interval '7 days' 등)는 필요에 따라 조정한다.

5.1 Activation — 가입 후 24시간 내 첫 산책 완료율

select
  count(*) filter (
    where exists (
      select 1 from walks w
      where w.owner_id = p.id
        and w.ended_at is not null
        and w.ended_at < p.created_at + interval '24 hours'
    )
  )::float / nullif(count(*), 0) as activation_rate_24h
from profiles p
where p.created_at > now() - interval '30 days';

5.2 Retention — D7 리텐션 (가입 7일 후에도 산책 기록이 있는 비율)

select
  count(*) filter (
    where exists (
      select 1 from walks w
      where w.owner_id = p.id
        and w.started_at::date = (p.created_at::date + 7)
    )
  )::float / nullif(count(*), 0) as d7_retention
from profiles p
where p.created_at < now() - interval '7 days'
  and p.created_at > now() - interval '60 days';

5.3 주간 활성 사용자(WAU) 추이

select date_trunc('week', started_at) as week, count(distinct owner_id) as wau
from walks
where started_at > now() - interval '12 weeks'
group by 1 order by 1;

5.4 Referral — 동네친구 매칭 → 하트 전환율

select
  count(distinct ne.user_a) + count(distinct ne.user_b) as matched_users,
  count(distinct pl.liker_id) as users_who_gave_heart,
  count(distinct pl.liker_id)::float
    / nullif(count(distinct ne.user_a) + count(distinct ne.user_b), 0) as heart_conversion
from neighbor_encounters ne
left join pet_likes pl on pl.liker_id in (ne.user_a, ne.user_b);

5.5 Safety — 분실 신고 평균 해결 시간

select
  avg(updated_at - created_at) as avg_time_to_resolve,
  percentile_cont(0.5) within group (order by (updated_at - created_at)) as median_time_to_resolve
from lost_cases
where status = 'resolved'
  and created_at > now() - interval '90 days';

5.6 알림 → 재방문 상관관계 (다이제스트가 실제로 산책을 유도하는가)

select
  n.trigger_key,
  count(*) as sent,
  count(*) filter (
    where exists (
      select 1 from walks w
      where w.owner_id = n.user_id
        and w.started_at between n.sent_at and n.sent_at + interval '24 hours'
    )
  )::float / nullif(count(*), 0) as walk_within_24h_rate
from notification_outbox n
where n.sent_at > now() - interval '30 days'
group by 1 order by 2 desc;
이 쿼리들은 참고용 인덱스 없이도 지금 규모(수백~수천 행)에서는 충분히 빠르다. 사용자가 크게 늘면 owner_id, started_at 등에 인덱스가 있는지 explain analyze로 확인한다.

#6. North Star Metric 제안

"주간 완료 산책 수(Weekly Completed Walks)"를 제안한다 — 가입자 수나 다운로드 수보다 이 지표가 낫다.

  • 산책 완료는 하트·동네친구·리마인더·분실 신고 예방까지 대부분의 핵심 기능이 실제로 발동하는 트리거이기 때문에, 이 숫자가 오르면 나머지도 대체로 같이 오른다.
  • §5.3 쿼리(WAU)와 함께, select count(*) from walks where started_at > date_trunc('week', now()) 로 주 단위 산책 완료 수를 바로 볼 수 있다.
  • 다운로드 수는 마케팅 예산 없이 유기적으로만 늘기 때문에 노력과 무관하게 움직이는 반면, 산책 완료 수는 앱 내부 개선(리마인더 타이밍, 하트 보상, 온보딩 마찰 감소)으로 직접 움직일 수 있는 지표다.

기존에 합의한 "첫 결제 스프린트"의 제약(거의 풀타임 1인, 마케팅 예산 0)을 그대로 반영한다.

#8. 코호트·리텐션 관점

Phase 1 단계에서도 가입 주차별 코호트 리텐션 곡선은 SQL로 볼 수 있다 — 아래는 가입 후 0~4주차 리텐션을 코호트별로 뽑는 예시다.

with cohorts as (
  select id as user_id, date_trunc('week', created_at) as cohort_week
  from profiles
),
activity as (
  select owner_id as user_id, date_trunc('week', started_at) as active_week
  from walks
)
select
  c.cohort_week,
  extract(week from age(a.active_week, c.cohort_week)) as weeks_since_signup,
  count(distinct a.user_id) as active_users
from cohorts c
join activity a using (user_id)
where a.active_week >= c.cohort_week
group by 1, 2
order by 1, 2;

가입 주차가 아직 몇 주 안 쌓였다면 이 쿼리 결과는 희소할 수 있다 — Phase 1의 한계를 보여주는 지표이기도 하다. 코호트 수가 늘어날수록(Phase 2 전환 신호) SDK 기반 대시보드로 옮기는 편이 유지보수가 쉬워진다.

#9. 리스크와 트레이드오프

  • SQL 임시 계측의 한계: 화면 조회, 버튼 클릭처럼 "일어났지만 DB에 안 남는" 행동은 Phase 1에서 영원히 안 보인다. 이걸 보려면 결국 Phase 2 SDK가 필요 — 무리해서 SQL로 흉내내려 하지 않는다.
  • 개인정보와의 충돌: Phase 2에서 SDK를 붙일 때, 위치 데이터를 이벤트 속성으로 함께 전송하지 않도록 주의해야 한다(정책서 §2의 최소 공개 원칙과 충돌 방지).
  • 1인 운영의 현실: 대시보드를 만들어도 매주 들여다볼 사람이 본인 하나뿐이라는 전제 — 지표 개수를 늘리기보다 §6의 North Star Metric 하나를 우선 습관적으로 확인하는 것이 실제로 더 유효하다.
  • 조기 A/B 테스트 지양: 지금 규모에서는 표본이 작아 A/B 테스트 결과의 통계적 유의성을 확보하기 어렵다 — Phase 3로 미루는 것이 맞는 판단이다.
